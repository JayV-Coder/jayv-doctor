title: SSO corporativo (SAML 2.0) com mapeamento de grupos
labels: feature, frontend, backend, security, M01-org, mobile, P1
---
## Escopo
- SAML 2.0 do Supabase Auth por Organização: domínios verificados por TXT de DNS e metadados do IdP (Entra ID, Okta, Google Workspace).
- "Exigir SSO" para os domínios verificados: login por senha e magic link bloqueado para esses e-mails.
- JIT provisioning: primeiro login cria o Vínculo conforme o mapeamento grupo → Papel (atributo `groups`). Mudança no grupo atualiza o Papel no login seguinte.
- SCIM 2.0 opcional para desprovisionamento automático (remover usuário no IdP remove o Vínculo).
- **Tela 23:** a seção de SSO.

## UI — Tela 23
```text
┌──────────────────────────┐
│ ← SSO e políticas  v1.0  │
│ SAML 2.0          [Ativo]│
│ Domínios acme.com.br     │
│ Metadados IdP [https://…]│
│ Exigir SSO          [on] │
│ AID-Admins → Admin       │
│ Políticas avançadas …    │
└──────────────────────────┘
```

## Critérios de aceite
- **Dado** "Exigir SSO" ativo, **quando** alguém tenta magic link com `@acme.com.br`, **então** é redirecionado ao IdP.
- **Dado** um usuário removido no IdP via SCIM, **então** o Vínculo some e as sessões são revogadas em < 5 min.

title: Políticas avançadas (IPs permitidos, sessão, MFA para todos, papéis customizados)
labels: feature, frontend, backend, security, M01-org, P1
---
## Escopo
- Lista de IPs permitidos por Organização (CIDR), aplicada na API e no PostgREST (verificação na API e policy RLS com `inet` da requisição, via header confiável do LB).
- Duração máxima de sessão e de inatividade por Organização.
- MFA obrigatório para todos os Papéis (opcional por Organização).
- **Papéis customizados:** permissões granulares (`incidents.review`, `connectors.manage`, `raw_logs.download`…) compostas em papéis próprios. Os 4 papéis padrão viram presets. É a migração da matriz de {{#06}} para permissões.
- Política de exportação: bloquear download de Log bruto e de relatório para certos papéis.

## Critérios de aceite
- **Dado** um IP fora da lista, **então** a API e o PostgREST respondem `403`, e a tentativa é auditada.

title: Cobrança com Stripe Billing (assinatura e excedente de uso)
labels: feature, frontend, backend, M01-org, P1
---
## Contexto
A v0.1 mede e impõe Cotas ({{#31}}). Agora elas viram cobrança.

## Escopo
- Produtos e preços no Stripe: planos (Piloto, Profissional, Empresarial) com assinatura mensal ou anual e **cobrança por uso** (Meters) para diagnósticos e eventos excedentes.
- Envio de uso: job diário que publica `usage_records` como meter events, de forma idempotente por (tenant, recurso, dia).
- Checkout para assinatura e Customer Portal para pagamento, faturas e cancelamento.
- Meios brasileiros: cartão e boleto; Pix se disponível na conta.
- Dados fiscais (CNPJ, endereço) e emissão de NFS-e por integração com um emissor (ticket filho).
- Webhooks do Stripe (`customer.subscription.*`, `invoice.*`) atualizam `tenants.plan` e `plan_limits`. A inadimplência gera aviso e, após a carência, o modo somente leitura.
- **Tela 22:** plano atual, opções, excedente do ciclo, cobrança e portal.

## UI — Tela 22
```text
┌──────────────────────────┐
│ ← Plano            v1.0  │
│ ┌ Profissional [Atual] ─┐│
│ │ [PREÇO]/mês · limites ││
│ └───────────────────────┘│
│ Empresarial [Falar c/ vendas]
│ Excedente: 120 diag.     │
│ Pagamento / Faturas / NF │
│ [Gerenciar no portal]    │
└──────────────────────────┘
```

## Critérios de aceite
- **Dado** 120 diagnósticos acima da Cota no ciclo, **então** a fatura seguinte tem o item de excedente correto, sem duplicidade em reprocessamentos.

title: Alta disponibilidade, SLA e página de status
labels: chore, infra, database, P1
---
## Escopo
- Supabase: compute dedicado, read replica para dashboards e leituras pesadas (com o roteamento de leituras na API) e PITR com retenção de 14 dias.
- Cloud Run com `min-instances` na API, multi-zona (regional) e Cloud Armor com regras WAF.
- Plano de recuperação de desastre: RTO ≤ 4 h e RPO ≤ 15 min, com drill semestral documentado.
- Página de status pública (componentes: API, ingestão, diagnóstico, conectores) com histórico de incidentes.
- SLOs e error budgets: disponibilidade da API 99,9%, ingestão p95 < 2 min, diagnóstico p95 < 2 min. Os relatórios mensais de SLO usam {{#34}}.
- Contratos: SLA por plano e créditos por indisponibilidade.

## Critérios de aceite
- Drill de failover e restauração executado dentro das metas de RTO e RPO.

## Escopo

title: Conectores adicionais (AWS CloudWatch, Azure Monitor, MuleSoft)
labels: feature, backend, M02-connectors, P2
---
## Escopo
- **AWS CloudWatch Logs:** IAM Role com External ID (sem chave), `FilterLogEvents` com Checkpoint por timestamp e token, e mapeamento de `requestId` e X-Ray `traceId`.
- **Azure Monitor / Log Analytics:** service principal ou federated credential, consultas KQL de uma allowlist, e Application Insights `operation_Id` como trace.
- **MuleSoft Anypoint Monitoring:** Connected App, logs de aplicações CloudHub e `correlationId`.
- Todos passam pela suíte de contrato de {{#14}} e ganham um wizard no padrão da Tela 12.
- Priorização final pela demanda dos clientes do piloto.

## Critérios de aceite
- Cada conector com teste E2E em conta de teste e documentação de permissões mínimas.
